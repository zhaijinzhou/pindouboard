## 1. 技术决策

### Q-01 框架选型 → **已决策：原生小程序**

| 维度 | 原生 | Taro | uni-app |
|---|---|---|---|
| 图像处理性能 | 直接调`wx.*` 与 Canvas 2D，无中间层 | Canvas API 需适配层，图像热点可能引入开销 | 同 Taro |
| 主包体积（§1.1 要求「静态 JSON 打包」） | 可精确控制 | 引入运行时后有额外开销 | 同 Taro |
| 启动耗时（目标 <1.5s） | 最优 | 有框架初始化开销 | 同 Taro |
| P0 功能开发速度 | 略慢（无模板语法） | 快 | 快 |

**决策理由**：本项目的性能瓶颈集中在**像素化与 PNG 编码**（文档 P-03），而这两处必须落到 Canvas 2D 与文件 API 上。跨端框架在这条链路上只能提供适配层而非优化，反而增加不确定性；且文档明确本期无服务端、无云端接口，跨端复用收益为零。

**代价**：WXML 模板需手写，无数据绑定糖。已通过全局 WXSS 设计变量与组件化样式缓解。

**落地**：`miniprogram/` 原生工程，无 npm 依赖、无构建步骤，开发者工具直接打开即可运行。

### Q-02 图像处理库 → **已决策：不引入第三方，全部自实现**

**决策理由**：
1. 需要的算法（像素化、主导色、ΔE、BFS、洪水填充、RLE）均为**纯数组运算**，无矩阵/卷积级依赖，第三方库（如 `pixelmatch`、`image-js`）提供的核心能力我们只用得上很小一部分；
2. 第三方库普遍面向浏览器（依赖 `document` / `ImageData` 构造器），在小程序端要么打补丁要么改写，省不下多少工作量；
3. 自实现可保证 `core/` `color/` 层零依赖、零平台绑定，**可在 Node 中直接跑单测**（这是本项目单测覆盖率能达到 246 项的前提）；
4. 包体积可控，符合 §1.1「静态 JSON 打包」的思路。

**落地**：全部自实现，见 `core/`（5 个算法模块）、`color/`（色彩科学 + 匹配）、`utils/codec.js`（编码）。

### Q-04 `cells` 存储格式与压缩方案 → **已决策：色号字典 + RLE**（⚠️ 结论与原文档建议不同）

#### 结论

原文档 §3.2 建议 `cells` 采用稀疏键值对 `{ "行,列": "色号" }`。**本项目实测发现该方案反而更大**，理由如下。

#### 实测数据（单格编码成本）

| 格式 | 单格开销 |
|---|---|
| 稀疏键值 `"12,13":"H21",` | **15 字符** |
| 密集数组 `"H21",` | 7 字符 |
| 密集数组 `"",`（空格） | 3 字符 |

坐标键 `"12,13":` 本身的开销就超过了一个完整短色号。除非空格占比极高，稀疏结构在任何真实图纸上都不占优。

#### 四种场景实测对比（字符数）

| 场景 | 稀疏键值 | 密集数组 | 稀疏节省 |
|---|---|---|---|
| 29 格满图 | 12615 | 5887 | **−114%** |
| 29 格半空 | 6300 | 4203 | −50% |
| 52 格满图 | 40560 | 18928 | **−114%** |
| 52 格半空 | 20280 | 13520 | −50% |

#### 采用方案

拼豆图纸的色块天然成片相连，**行程编码（RLE）** 是这类数据的最优通用压缩：

```json
{
  "cols": 29, "rows": 29,
  "dict": ["H21", "H85", "H7"],
  "rle": [120, 0, 15, 1, 200, 2, ...]
}
```

- `dict`：色号字典，按首次出现顺序
- `rle`：行优先展开的 `[长度, 字典下标]` 交替序列
- 解码为 O(n) 单次扫描，无需 `JSON.parse` 大对象

相对 §3.2 稀疏格式，52 格满图约压缩 **90%**。

**重要说明**：内存中的图纸模型**仍保留 §3.2 的稀疏 `cells` 结构**以维持对外契约与可读性；RLE 仅用于**存储与传输**环节。两者通过 `utils/codec.js` 的 `toSparse` / `fromSparse` 互转。

**落地**：`utils/codec.js`，单测覆盖往返无损性。

### Q-07 库存豆柜录入方式 → **已决策：手动输入 + 按图纸批量填充**

**未采用拍照识别 / 扫色号贴的理由**：
- 拍照识别需要额外的 OCR + 颜色识别能力，且豆子在袋中反光、透视变形严重，识别准确率不足以让用户直接信任；
- 豆柜是**低频操作**（补货时用），手动输入的成本可接受；
- 「按图纸批量填充」覆盖了真实高频场景：出完图顺手把用量录进豆柜。

**落地**：`pages/cabinet/cabinet.js`，两种录入方式均可。

### Q-08 库存色不足时的降级策略 → **已决策：三级降级 + 显式提示**

这是本次决策中**对用户体验影响最大**的一条。

| 级别 | 条件 | 行为 |
|---|---|---|
| 1. 正常 | 库存色集与色库有交集 | 限定在交集内匹配 |
| 2. **回退全色库** | 库存色集与色库**完全无交集** | 回退到全色库匹配，同时体检提示「库存不足」 |
| 3. **压缩颜色数** | 库存色少且图用色多 | 颜色数上限降级，把用量归并到库存内色号 |

**关键设计**：宁可**出图并告知缺货**，也不让用户面对一个无法生成的空白页面 —— 因为「知道缺什么」本身就是豆柜功能的核心价值。

**配套**：清单页提供库存缺口对照（`analyzeInventory`），显示「需 X / 有 Y」，并可直接跳转豆柜更新。

**落地**：`color/palette-loader.js` `selectCandidates`（级别 1、2）、`color/match.js` `limitColorCount`（级别 3）、`render/checklist.js` `analyzeInventory`（提示）。

### D-02 ΔE 匹配实现细节与色差容差 → **已补齐**

#### 算法选择：CIEDE2000（默认）+ ΔE76（剪枝）

| 项 | 取值 | 依据 |
|---|---|---|
| 默认算法 | **ΔE2000** | 修正了ΔE76 在蓝绿色区域的显著偏差，且更符合人眼对明度敏感、对色相不敏感的特性 |
| 粗筛算法 | ΔE76 | 公式简单、速度快，用于剪枝阶段 |
| 可接受色差上限 | **ΔE = 14** | CIE 分级中 ΔE>10 属「明显差异」；14 留给匹配器一点余量，超出即进入体检提示 |
| 色相剪枝角 | **25°** | 超出此角度的候选色在 Lab 空间的 L/a/b 差异必然已被 ΔE76 反映，不可能成为最近邻 |

**正确性验证**：ΔE2000 实现已与 **Sharma, Wu & Dalal (2005) 官方测试数据**（13 组用例，含色相跨 0°/360° 边界、中性色分支、大跨度三类最易写错的场景）逐条比对，最大偏差 **1e-15**；同时与按CIE 142-2001 原文逐字转写的独立参考实现交叉验证，完全一致。

> 这项验证至关重要：ΔE 算错不会报错，只会让匹配结果**静默劣化**。

#### 两阶段匹配（P-05 剪枝）

1. **粗筛**：按色相角预筛候选集（灰色不参与剪枝，避免漏掉无彩色匹配），用 ΔE76 取前 8 名
2. **精算**：对8 个候选做 ΔE2000，取最近者

52 格四板场景：2704 格 × 221 色 ≈ 60 万次比较，经剪枝后降至约 2 万次ΔE2000 精算。

### D-03 主导色算法区域划分规则 → **已补齐**

#### 规则

1. **区域划分**：以目标格为单位，格内再划分 `q×q` 子采样网格（q = 3）
   - 依据：q=1 时压缩噪点会被当成独立颜色；q=3 时 9 个子样本已足以反映视觉主导色，计算量可控
2. **量化**：按 32 步长对 RGB 三通道做桶量化
   - 依据：步长过小则噪点独立成色，过大则真实渐变被抹平；32 步长（约 8 级/通道）既能合并压缩噪点，又保留主要色块边界
3. **取主色**：统计各桶频次，取最高者；用桶内实际像素的均值输出（避免量化带来的阶梯误差）
4. **回退条件**：最高频次 < 3 时，认为该格颜色过于分散（如渐变天空），**回退到区域均值**

#### 实现要点：为何要「高采样 → 聚合」两步

像素化阶段先输出 `cols×3 × rows×3` 的高采样格点阵，再聚合为最终尺寸。

**原因**：只有在子像素级别统计频次，才能真正判断「哪个颜色占主导」。若先聚合成一格再统计，频次信息已丢失，D-03 的规则就无从谈起。

### D-04 BFS 杂色合并相似度阈值默认值 → **已补齐：ΔE = 12**

#### 依据

CIE 色差可辨识度分级：

| ΔE 范围 | 人眼感知 |
|---|---|
| < 2.3 | 不可察觉 |
| 2 ~ 5 | 仅可察觉细微差异 |
| 5 ~ 10 | 察觉但可接受 |
| **> 10** | **明显差异** |

取 **12**：已越过「明显差异」界线——两个 ΔE<12 的颜色并排时肉眼基本分辨不出，却能把零碎色数量显著压下来。
- 取更小（如 5）：压缩不足，颜色数仍超标
- 取更大（如 20）：会吞掉真实的明暗层次

#### 算法：连通域 + 并查集（非朴素 BFS）

1. 按 4-邻域把同色格切分为初始连通域
2. 为每个域计算代表色（Lab 均值）与色号（域内出现次数最多者）
3. 并查集：若两个**相邻**域代表色的 ΔE < 阈值则合并
4. 迭代直到无新增合并，或达 4 轮上限（防止病态输入下震荡）
5. 簇内取格子数最多的色号；平票时取首次出现序更靠前的，**保证结果稳定可复现**

#### 关键设计：为何用 Lab 均值而非直接取一方色号

直接取某一方色号会引入**系统性偏差** —— 合并结果总向初始占优的一方偏色，累积后整图色调会漂移。用 Lab 均值可避免此问题。

#### 豆子类型联动（§2.2「fusion 影响配色策略宽松度」）

`fusion` 加热融合的阈值放大 1.25 倍 —— 熨烫过程会弱化相邻色差异，对更宽松的配色更宽容。

### D-05 Offscreen Canvas 导出具体实现 → **已补齐：三级策略**

#### 问题

`wx.canvasToTempFilePath` 对输出尺寸有机型相关上限，直接申请超大 Canvas 在中低端机上易触发内存崩溃。

#### 策略

| 级别 | 条件 | 行为 |
|---|---|---|
| 1. 单图导出 | 尺寸在上限内 | 整张导出，最高分辨率 |
| 2. **分板导出** | 超出上限 | 按板拆成多块并排渲染，一次出图；打印后沿分板线裁切 |
| 3. 降级导出 | OffscreenCanvas 不可用 | 回退页面 Canvas，并明确告知用户分辨率受限 |

#### 尺寸选择不是越大越好

- 目标最短边 **2048px**（P-01 要求，保证色号打印清晰）
- 单格边长封顶 **64px**：超过后对打印清晰度无实质增益，反而显著增加体积与内存
- 单格下探至 **26px**：低于此值色号文字开始糊

#### 预览与导出解耦

屏幕预览按容器自适应（单格 6~28px）保证流畅，导出时才上高分辨率。两者不共用尺寸，避免「为了导出清晰度牺牲预览帧率」。

## 4. 其他补充决策

### 孤立块判定规则（文档 §2.1 未定义边界情形）

**规则**：一格为孤立格 ⟺ 存在 ≥2 个有效邻居，且**全部有效邻居均异色**。

**为何不用「异色邻居数 ≥ 4」的固定阈值**：贴边格天然邻居更少（角落仅 2 个、边缘 3 个），固定阈值会让所有贴边格永远无法被判为孤立，产生「边缘检测不到碎片」的**系统性盲区**。比例型规则保证边界与内部行为一致。

### 库存数据结构（文档未定义）

```js
{ [brand]: { [beadSize]: { [code]: quantity } } }
// 例：{ MARD: { '5mm': { H1: 120, H7: 30 } } }
```

### 色库版本号（§8「待定义」）

定义为 **`0.2.0`**，与文档版本对齐，便于追溯「某张图纸是用哪版色库出的」。

### 抖动默认关闭（§2.1 已定，此处补充说明）

Floyd-Steinberg 抖动通过量化误差扩散模拟中间色，能提升照片渐变过渡，但会产生大量零碎色，与「控制颜色数量」的核心诉求**直接冲突**。

已在 `core/algorithm.js` 完整实现（4 个邻居按7/16、3/16、5/16、1/16 权重扩散残差），验证可用，仅在用户显式开启时启用。
